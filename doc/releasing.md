# Releasing `skref`

A release is one merged PR. Merging a version bump to `main` tags it, and the tag
publishes everything: crates.io, the prebuilt binaries and GitHub Release, the
Homebrew formula, and the moving `v1` tag. There is no manual `git tag`,
`cargo publish`, or tag move.

Pick the version by what changed: additive features → minor bump (`1.0.0` → `1.1.0`);
breaking API changes → major bump; fixes only → patch.

## 1. Bump the version (via a PR)

`main` has branch protection requiring a PR review approval, so even a one-line
version bump goes through a PR.

```bash
git checkout -b release/X.Y.Z
# edit Cargo.toml: version = "X.Y.Z"
cargo build            # refreshes skref's entry in Cargo.lock
git commit -am "Release vX.Y.Z"
git push -u origin release/X.Y.Z
gh pr create --title "Release vX.Y.Z" --body "Bump version for the … release."
```

Get the PR approved and merged. That's the whole release.

## 2. What happens on merge

1. [`tag-release.yml`](../.github/workflows/tag-release.yml) runs on every push to
   `main`. It reads `Cargo.toml`'s version and, if `vX.Y.Z` doesn't exist yet, tags
   the pushed commit. Pushes that don't change the version find the tag and do
   nothing. The tag is created with the Alephic Bot app token: a tag created with
   `github.token` would not trigger the workflows below.
2. The `vX.Y.Z` tag fires two workflows (both trigger on tags matching
   `**[0-9]+.[0-9]+.[0-9]+*`):
   - [`publish-crate.yml`](../.github/workflows/publish-crate.yml) publishes to
     crates.io using **Trusted Publishing** (OIDC, no stored token).
   - [`release.yml`](../.github/workflows/release.yml) (generated by `dist`) builds
     the prebuilt binaries and the GitHub Release, then runs two custom jobs:
     - [`homebrew.yml`](../.github/workflows/homebrew.yml) regenerates
       `Formula/skref.rb` in
       [alephic-ai/homebrew-tap](https://github.com/alephic-ai/homebrew-tap) from the
       release's tarballs and `.sha256` sidecars. The formula is generated, never
       hand-edited: fix a bad one in `homebrew.yml`, not in the tap.
     - [`move-major-tag.yml`](../.github/workflows/move-major-tag.yml) moves `v1`
       to the release once it is announced (see below).

Both custom jobs are wired in through `dist-workspace.toml` (`publish-jobs` and
`post-announce-jobs`); after changing either list, re-run `dist generate` to refresh
`release.yml`.

Check the result: `gh run list -w "Tag release"` then `gh run list -w Release`.

## The `v1` major tag

The Action is consumed as `alephic-ai/skref@v1`. `@v1` reads that commit's
`Cargo.toml` version and downloads the matching binaries, so `v1` must point at the
latest `v1.x.y` release commit. `move-major-tag.yml` does this after the release is
out, and only when the release is the highest stable `vN.x.y`: a prerelease or a
backported patch on an older minor leaves `vN` where it is. A new major (`v2.0.0`)
creates `v2` the same way.

The bare `v1` tag does **not** match the release trigger pattern, so moving it
publishes nothing.

## Recovering

- **Tagging failed** (e.g. the bot token couldn't be minted): fix the cause, then
  re-run it with `gh workflow run tag-release.yml` (it tags `main`'s current version
  if that tag is missing).
- **A release workflow failed after the tag exists**: re-run the failed jobs from the
  Actions tab. `tag-release.yml` won't re-tag an existing version.

## Optional: dry-run the publish

```bash
gh workflow run publish-crate.yml -f dry_run=true
```
